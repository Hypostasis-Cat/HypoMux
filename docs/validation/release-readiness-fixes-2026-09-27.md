## 已完成修复

### 快捷添加分流规则

- 保存时传递最新快照的 `match_order` 和 `revision`，调用后端锁内版本检查，保留 IP 优先等自定义顺序。
- 预览与提交之间发生 AI/MCP 或其他编辑器写入时，拒绝过期提交；保留对话框和用户选择，显示错误，允许重新提交。
- 最新预览出现用户尚未确认的出口冲突时，先展示该冲突，要求再次确认更新，避免把“添加”悄悄变成覆盖。
- 回归覆盖自定义顺序、并发修改保护、冲突重新确认及保存失败后的草稿保留。

### TUN：从环境推断改为实际启动结果

| 场景 | 普通启动 | 强制启动 |
| --- | --- | --- |
| 第三方隧道路由重叠 | 展示警告，允许继续 | 仅作为信息，不阻止启动 |
| 启动前公共测试域名解析失败 | 记录诊断，读取 Core 已配置的 DNS 上游继续启动 | 不发起这些解析测试，直接读取本地 `dns.status` 配置 |
| 启动后外部站点探测失败 | 保持运行，展示未验证联网的提示 | 不执行探测 |
| 运行期外部站点持续失败 | 更新诊断提示，不再据此自动停机；探测恢复后清除提示 | 不执行周期联网探测 |
| 地址检查 | 检查接口地址和路由地址占用 | 跳过路由占用推断和不完整检查错误，避开已知本地接口地址 |
| 缺少核心文件、无有效网卡、源地址重复、无权限或真实 TUN 创建失败 | 明确失败 | 同样明确失败，不伪造启动成功 |

未知软件、企业网络和受限测试站点不再需要依赖逐个产品名称加入允许列表来通过启动。现有软件名称识别仅辅助诊断，不再拥有禁止启动的决定权。

DNS 兜底读取正在运行的 Core 的规范化配置，避免在桌面重复维护服务商目录。保留用户的加密 DNS 策略、网卡绑定和传统 DNS 选择顺序；不会为了强制启动私自把加密 DNS 改成明文。现有 WFP 兼容降级、真实启动失败回滚和核心生命周期管理保持有效。

强制启动改变的是诊断门槛，不保证外部网络一定可达，也无法让缺失驱动、权限拒绝或非法配置变为成功。若实际访问失败，用户可手动停止。设置页中英文说明同步更新，预检缓存键加入强制启动设置，防止切换后复用旧检查。
