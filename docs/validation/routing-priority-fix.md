# 指定网卡 IP 规则优先级修复

## 问题与方案

`faa1af7` 引入的代理服务器网卡指定逻辑，将所有指定网卡的 IP 规则放到 DNS 和用户进程规则之前；2.5.9 的本地规则集热更新保留了这一行为。`0.0.0.0/0 → WLAN` 和 `::/0 → WLAN` 因而会截走游戏与 DNS 流量。规则保存时的排序本身正确。

修复后的顺序：

1. 流量嗅探、HypoMux 自身核心进程绕过。
2. DNS 接管（沿用 DNS 策略；`system` 不接管）。
3. 仅对已识别的第三方代理进程，应用指定网卡 IP 例外及兼容绕过；两者都排除命中用户进程或域名规则的连接。
4. DNS 解析后，按进程、域名、IP 顺序执行普通用户规则。
5. 未匹配流量走默认聚合。

IP 例外的冲突排除计算同时考虑非网卡出口，避免较宽的网卡规则吞掉更具体的非网卡规则。代理兼容绕过仍保留：未命中指定网卡例外和用户进程/域名规则的代理连接走系统直连。

## 热更新与升级

优先级排除条件引用所有出口对应的进程、域名规则集，包含当前为空的规则集。因此运行中添加或删除规则时不需要重写主配置，保留现有原子替换及失败回滚机制。

本次修复改变了主配置结构。安装包含修复的版本后应停止并重新启动聚合/TUN，以生成新主配置；旧版本中单纯重新保存规则不能修复顺序。现有连接沿用原路径，验证游戏分流时需要建立新连接。

## 验证

- 新增 `TestTUNRoutingPriorityAndHotReload`：覆盖 auto/off/system DNS 策略、有无代理兼容配置、IPv4/IPv6 兜底、具体网段、进程与域名重叠、校园网、代理名称/路径、DNS，以及规则热更新。
- 对生成的配置与规则集进行已知连接元数据的匹配断言，并运行随附 sing-box 的 `check`。匹配断言不模拟系统进程识别、嗅探或真实 DNS 解析。
- 使用 Go overlay 将生产代码替换为修复前的 HEAD，新增测试重现游戏、域名、DNS 被 WLAN 截走的失败；恢复修复代码后通过。
- 运行桌面服务层完整测试。未在反馈者的双网卡环境启动真实 TUN，仍需使用其游戏新连接和原配置进行现场验收。
