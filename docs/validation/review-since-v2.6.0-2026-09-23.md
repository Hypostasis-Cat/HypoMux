### 2. [P2] 单次连接的候选集合变化会清空自适应调度学习状态

- 位置：`engine/internal/proxy/adaptive_allocation.go:51–54`；调用链为 `dialUpstream → acquireTCP → performanceTable.acquire → adaptiveAllocation.choose`。
- `choose` 把本次连接过滤后的候选集合当作整个聚合池；一旦不同便调用 `reset`，清空权重、观察窗口并重设预热起点。
- 触发例：三张网卡中两张支持 IPv6、一张只支持 IPv4。IPv4 连接使用三张候选，IPv6 连接使用两张。两种连接交替出现时，即使用户没有修改网卡配置，也会反复重置。至少两张候选才进入此自适应分支，因此不是所有双网卡情况都会触发。
- 影响：“最大速度优先”丢失已学习份额；如果集合变化间隔小于 15 秒，可一直无法完成预热。三张以上网卡中的健康过滤或重试也可能形成同类候选子集变化。
- 复现：临时纯内存测试先设置三张网卡的学习状态为 `adapting`、份额为 `[0.5, 0.3, 0.2]`，依次使用两张和三张候选执行选择，结果变为 `warming-up`、`[1/3, 1/3, 1/3]`，预热起点被刷新。测试按应保留学习状态断言，失败。
- 建议：仅实际聚合池配置改变时重置全局学习状态；对受限候选集合采用独立分配状态或临时归一化已有份额，避免单次连接修改全局预热窗口。

### 3. [P2] AI 启动热点后可能显示错误密码和连接二维码

- 位置：`desktop/frontend/src/components/HotspotPanel.tsx:87` 及二维码的 `hotspotQRPayload(config)` 调用；后端入口为 `ai_tools.go` 的 `start_saved_hotspot`。
- 触发步骤：保存热点名称和密码 A；在工具箱把密码改成 B 但不保存；让 AI 或外部 MCP 使用已保存配置启动热点；回到工具箱扫码。
- 后端使用 A 启动，工具箱仍优先读取 `hotspotDraft.current` 中的 B。已有草稿时不会重新读取已保存配置。二维码可用性只比较 SSID，没有确认密码属于当前热点会话。
- 影响：页面显示热点正在运行，却提供错误密码；手机扫码不能连接。若未保存草稿还改变了 SSID，则二维码入口会一直不可用。
- 复现：临时 React 测试模拟已保存密码 `saved-password`、未保存草稿 `unsaved-password`，状态返回同名运行中热点；实际二维码内容为 `WIFI:T:WPA;S:My hotspot;P:unsaved-password;;`。测试按应使用实际会话凭据断言，失败。
- 快捷开关已有手动同步草稿的代码，但 AI/MCP 启动不经过该前端分支，不能覆盖此场景。
- 建议：把编辑草稿与当前会话凭据分开；检测到外部启动时读取与该会话对应的配置后再开放密码/二维码，并保留尚未保存的编辑。

### 4. [P2] 官网子模块缺少映射，主仓库无法正常初始化它

- 位置：根目录 `website` Git 条目。
- HEAD 以模式 `160000` 保存了官网提交 `9a5bf0e12f3c710208a26f18b96b090d73750158`，却没有提交 `.gitmodules`。
- 复现：`git submodule status` 返回 `fatal: no submodule mapping found in .gitmodules for path 'website'`。
- 影响：本机已有独立官网 checkout 会掩盖问题，但新克隆无法从主仓库得知子模块 URL，也不能正常递归初始化官网源码。这不等于当前已部署官网不可用。
- 建议：若官网作为子模块管理，提交完整的 path/URL 映射；若保持独立仓库，则移除主仓库中意外加入的 gitlink，明确独立获取方式。
