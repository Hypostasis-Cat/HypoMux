# v2.5.9 用户反馈优化方案与排查清单

## 已确定问题及实现

| 反馈 | 确定问题 | 本次实现 | 验收要求 |
| --- | --- | --- | --- |
| 图 1 | 多项 PowerShell 检查共用 4 秒，后续超时会丢弃已完成结果；未完成被当作风险 | 总预算调整为 8 秒，每个检查阶段输出快照，保留最后一个完整快照；未完成项改为信息 | 后续超时/输出截断不能掩盖已经发现的第三方默认路由冲突 |
| 图 3 | 旧 config.json 迁移失败，却指向未生成的 settings.json | 记录实际失败输入路径；提示冲突端口的字段名、值和修复示例，说明可以备份并重命名旧文件后使用默认设置 | 原配置不被覆盖、目标文件不生成、启动阻断保持有效 |
| 图 4 | 虚拟网卡、转发、ICS 存在就被当作接管风险 | 降为环境信息，不单独触发风险确认；真实第三方 TUN 默认路由仍阻断 | 环境信息不阻断；检查不完整也不能消除已发现的真实冲突 |
| 图 6 | 重复源 IP 到核心启动才暴露，提示不包含网卡身份 | 系统代理和 TUN 启动前共用源地址校验，TUN 预检显示阻断项；列出两张网卡名称、接口索引和 IP，包含等价 IPv6 地址 | 单网卡可继续；不同源地址可继续；重复源地址不能启动核心 |
| 图 7 | TCP 结果覆盖 ICMP 丢包率，本地错误被固定写成 1231，无样本显示 0 ms | TCP 决定链路可用性，ICMP 保留独立测量；保留真实系统错误码和消息；无有效丢包测量使用 -1，界面显示 —；延迟需要至少一个成功样本，抖动需要两个 | TCP 成功不能抹掉 ICMP 丢包；TCP 失败不能制造 100% 丢包；本地失败与超时分开 |

当前方案保留 PowerShell 检查，未改成原生 Windows API。实际默认路由识别仍沿用现有名称规则，不宣称能够识别所有第三方网络接管方式。旧配置迁移仍采取不覆盖原文件的阻断策略，未自动改用户端口或新增重置按钮。

## 暂不推定根因的问题

- 图 2：Windows TUN 设备未就绪。需要完整 sing-box 启动日志、HypoMux 支持日志、Windows 版本、sing-box 版本，以及故障时 HypoMux-Tun 的设备状态。记录首次启动还是停止后重启/切换模式才发生。
- 图 5：TUN 后系统 DNS 解析超时。需要支持日志中完整 tun_connectivity 检查项、当时 settings.json、实际生成的 sing-box 配置、分流规则、DNS 策略、严格路由状态。记录关闭 HypoMux 时是否能解析域名。仓库已有 13501f1 路由优先级修复，本次未另改 DNS 路由或放宽联网验证。
- 图 6/7：两个接口同源地址以及绑定失败。需要故障时系统地址状态、路由和完整 TCP 绑定错误，确认真实重复地址还是地址选取/时序问题。本次不推定 Windows 地址分配有错，也未直接过滤用户网卡。

可请用户在故障发生时运行以下只读 PowerShell 命令并保存输出；无需修改网卡或停用 Hyper-V/ICS：

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Select-Object InterfaceAlias,InterfaceIndex,IPAddress,AddressState,PrefixOrigin,SuffixOrigin,SkipAsSource
Get-NetAdapter -IncludeHidden | Select-Object Name,ifIndex,Status,InterfaceDescription
Get-NetRoute -AddressFamily IPv4 | Select-Object InterfaceIndex,DestinationPrefix,NextHop,RouteMetric
Get-DnsClientServerAddress -AddressFamily IPv4
Get-PnpDevice -Class Net | Where-Object FriendlyName -like '*HypoMux*' | Format-List Status,Class,FriendlyName,InstanceId,Problem
```

用户发来的配置可以遮盖令牌、账号和代理凭据，保留端口、DNS、网卡信息与相关分流规则。图 3 如果需要进一步分析旧端口来源，只需旧 config.json 的 socks_port/http_port 字段及之前使用的版本。
