# 网络兼容性优化：路由机制与本地发现

## 本次行为

本次将部分兼容策略从软件名称名单提升为路由和接口状态判断。保留原有进程旁路、用户分流优先级、WFP/DNS 单次兼容重启，以及实际数据通路连续失败后的恢复机制。

- **双栈路由快照**：使用 Windows IP Helper 读取 IPv4/IPv6 活动路由、下一跳、接口类型、驱动描述、连接状态，以及路由和接口的总跃点。不依赖 PowerShell 来取得路由接管证据；共享服务等补充信息仍由原只读检查获取。一族检查失败不丢弃另一族已取得的证据，未启用的协议栈视为空表。
- **接管判断**：对 `/0` 至 `/3` 的大范围路由按最长前缀、总跃点排序。覆盖备用 VPN 默认路由、同代价竞争、`/1` 拆分默认路由，以及排除局域网后产生的 `/2`、`/3` 路由。隧道类型和驱动描述参与识别改名或未知软件；仅“非物理网卡”不足以阻断，避免误拦 Hyper-V 主机出口和普通虚拟网络。保留自身残留 TUN 的恢复入口。
- **地址避让**：TUN IPv4 地址同时避让全部接口地址和已连接接口上的专用路由，防止新建 `/30` 抢走 VPN 的内部网段。默认和 `/1` 路由不视为地址占用；更细路由按占用处理。常用候选耗尽后，在 RFC1918 三个地址池中按区间寻找完整空闲 `/30`，不逐个扫描地址。IPv6 的 `/126` 也会避让接口和路由占用，从预置 ULA 候选中选择。无法安全分配时返回错误，不修改其他网络。
- **本地设备发现**：在 TUN 接管边界排除 `169.254.0.0/16`、`224.0.0.0/4`、`255.255.255.255/32`；启用 IPv6 时再排除 `fe80::/10`、`ff00::/8`。覆盖 mDNS、SSDP、LLMNR 使用的组播目标和链路本地通信。保留 DNS 引导地址排除，系统 DNS 策略不额外添加引导地址。普通 RFC1918、ULA 与 FakeIP 不整体旁路。
- **运行期观察**：TUN 激活后记录基线，复用现有约 30 秒健康检查周期读取原生路由表。完整快照发生变化时记录摘要、候选冲突接口和路由观察结果；表项顺序或重复项变化不重复记录，失败扫描不覆盖完整基线。下一跳改变也能被识别。周期日志不输出整张路由表，不新增自动上传。

运行期观察只用于诊断，不因检测到其他软件而自动重启或抢回路由。现有健康检查仍依据真实聚合通路、物理出口和连续失败次数决定是否恢复网络；不新增静默降级系统代理或关闭严格路由。

## 自动化验证

新增可重放网络状态用例，覆盖：

- Radmin 备用/优先路由、同代价竞争、断开接口、残留自身 TUN。
- 重命名 WireGuard、未知隧道类型、名称含 VPN 的物理接口、Hyper-V 和普通虚拟出口。
- IPv4/IPv6 默认路由、拆分路由、碎片化大范围路由、VPN 私网路由及链路本地设备网络。
- 接口或 VPN 地址重叠、固定候选耗尽、三个私网地址池耗尽、地址池中的空隙、IPv6 ULA 避让。
- 三种 DNS 策略、IPv4/双栈下的设备发现排除及用户私网/FakeIP 规则保留。
- VPN 后启动、网关变化、重复快照、乱序、扫描失败及日志边界。

旧 PowerShell 默认路由选择测试由直接测试生产 Go 判断逻辑的场景集替代。原有配置生成、内置 sing-box `check`、路由优先级和热更新测试继续运行。

```powershell

go test ./...
```

## 边界与后续验收

这不是小米妙享、所有 VPN 或所有过滤驱动组合的实机认证。当前大范围接管识别限于 `/0`–`/3`；全部由更细路由组成的接管、没有可识别元数据的虚拟驱动、WFP/NDIS 过滤器之间的竞争仍可能需要进一步诊断。

路由排除发生在用户分流之前，因此上述链路本地、组播和有限广播目标不会进入聚合或用户 TUN 进程规则。它不保证应用选择正确的发现接口，不修改系统防火墙，不覆盖所有定向广播，也未修改 `.local`、单标签主机名或企业分流 DNS 的解析规则。严格路由的非 TUN 53 端口限制仍存在。普通局域网单播和应用专有协议仍需端到端验证。

运行期检查依赖现有 Snapshot/健康检查调用，强制绕过 TUN 检查时不会执行周期观察；不是独立的后台事件订阅服务，也不会自动热改旁路策略。

发布前应在真实设备验证：

1. 妙享/投屏先启动与后启动两种顺序：发现、连接、传文件、断开重连。
2. Radmin/WireGuard 的备用默认路由、专用网段和全局接管分别验证。
3. Wi-Fi Direct、移动热点、睡眠恢复和切换 Wi-Fi 后的发现与传输。
4. IPv4-only/双栈、严格路由开关、三种 DNS 策略下的互联网、DNS 和局域网单播。
5. 停止 HypoMux 后检查其他软件网络正常，确认只回收本应用拥有的资源。

## Teredo 启动误拦修复

初版将 `IF_TYPE_TUNNEL=131` 直接视为第三方 VPN 证据，且没有保留 Windows 的 `TunnelType` 子类型。用户报告正常 IPv4 出口与唯一 Teredo IPv6 默认路由 `::/0`（总跃点 331）并存时被阻止启动。此前全量测试通过没有覆盖这一场景，不能代表实际环境兼容性验证充分。

修复后读取原生隧道子类型，6to4（11）、ISATAP（13）、Teredo（14）只保留网络环境信息。普通隧道类型和通用的 `Tunnel` 名称也不再单独触发阻断；已识别的 TUN/VPN 名称及驱动证据仍参与竞争判断。未知隧道可能不能被主动阻断，继续依靠实际数据通路验证和故障恢复。

新增用例覆盖截图拓扑、三种过渡隧道、改名后的 Teredo、普通未知隧道，以及同时出现真实 WireGuard 拆分默认路由时仍保留该 VPN 的检查。无需关闭系统 Teredo、IPv6 或防火墙。

## Teredo 修复后的兼容性复审

进一步复审确认并修复三处边界问题：

1. 大范围路由判断此前仅在 `/0`–`/3` 之间比较，忽略更具体的路由。两个优先级更高的 `/4` 完全覆盖 VPN 的 `/3` 时仍可能阻止启动。现用完整路由前缀覆盖关系判断候选是否还可能被选中，前缀更长优先于跃点；只有部分覆盖时保留原检查。IPv4 和 IPv6 均有复现测试。
2. 地址分配此前使用双栈诊断扫描，IPv6 查询或可选网卡类型/描述查询失败会连带阻止 IPv4 分配。现仅查询正在分配的地址族，可选元数据失败不丢弃已取得的路由；路由表和接口连接状态等必要证据失败仍返回错误。自身残留接口额外按原生接口索引排除。预检诊断仍保留完整错误信息。
3. IPv6 固定候选全部被占用不等于整个 ULA 池耗尽。现保留首选地址顺序，候选耗尽后在 `fd00::/8` 中按前缀树寻找完整空闲 `/126`。全部 ULA 确实占用时仍拒绝分配。

验证：复现用例在修复前失败，修复后通过；地址树搜索使用 `/28` 内全部 65,536 种主机占用组合与简单枚举结果比较；Windows API 替身测试覆盖可选元数据失败、必要接口查询失败和地址族隔离。桌面 `go test ./...` 及显式只读 Windows 集成检查通过，未启停用户网络或改动系统路由。

这些检查仍不代替妙享、投屏和第三方过滤驱动的设备端验收；没有把“测试通过”解释为所有兼容问题均已排除。
