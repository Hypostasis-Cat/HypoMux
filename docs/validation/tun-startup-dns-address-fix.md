# TUN 启动：DNS 回退预算与接口地址冲突

## 证据与修复范围

- 2026-09-09 20:22:12 的支持日志进入 TUN 启动；预检通过，已连接提权服务核心。20:22:17 在 `dns_validating` 失败，DoH 与传统 DNS 回退均报 deadline exceeded。此时尚未启动 sing-box，不是原截图中设备未就绪故障的直接复现。
- GitHub issue #75（https://github.com/Hypostasis-Cat/HypoMux/issues/75）报告 Hyper-V 接口使用 172.19.0.1/20，和固定 TUN 地址 172.19.0.1/30 冲突，sing-box 报 `set ipv4 address: The object already exists`。
- 两个故障处于不同阶段；不能据此断言原来的 `The device is not ready for use` 已经解决。

## 实施方案

1. 自动 DNS 将剩余总预算的一半保留给绑定原出口的传统 DNS。DoH 各批次根据自己的实际截止时间分配预算；传统 DNS 的 UDP、TCP 和后续服务器也分别获得尝试时间。总查询预算仍受原上下文约束。显式指定 DoH 提供商仍不会自动改用明文 DNS。
2. 生成 TUN 配置前枚举所有接口的 IPv4 网段，包括未参与聚合的虚拟接口。保留可用的历史地址，否则从 RFC1918 候选 /30 网段中选择不重叠地址；不使用 FakeIP 或 CGNAT 地址池。无法完成检查或候选耗尽时明确报错。
3. 单次启动的双栈配置和 IPv4 回退配置共用选定地址。核心从已暂存的配置读取实际 TUN IPv4 地址进行就绪检查，不再硬编码 172.19.0.1。
4. 支持日志记录所选 TUN 地址以及 DNS 验证成功时的策略、出口、传输和服务器。

## 验证范围

回归测试覆盖：所有 DoH 静默超时且首个传统 DNS 不响应时仍能由后续服务器解析；显式 DoH 超时不降级；Hyper-V 同地址和仅网段重叠；VPN 覆盖整个候选网段；无可用候选；动态地址的配置生成、IPv4 回退和核心就绪检查；缺少自有接口地址时在清理设备前拒绝启动。

该选择器检查接口地址网段，不声称穷尽远端 VPN 路由或消除选择后系统网络变化造成的竞态。未操作反馈用户的网络环境；实际安装包仍需用户复测。若全部 DNS 服务器确实不可达，启动仍会失败并保留联网验证。
