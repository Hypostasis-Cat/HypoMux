# HypoMux Wails v3 迁移计划

> 原则：功能与生命周期完整迁移，视觉全新设计；小步交付，每阶段有独立退出门禁。

## 0. 不可突破的约束

- v2.2.0 是功能、内容、配置和异常处理真值来源。
- 不因 UI 重构删除、合并或弱化功能。
- React 不承载网络业务。
- Wails Host 不长期管理员运行。
- 旧前端在完整验收前不删除。
- 不一次性实现全部页面。
- 每一阶段必须有构建、运行、视觉或真实 Windows 证据。

## 1. 阶段 P0：完整扫描与规划

交付：

- `feature-inventory.md`
- `ui-migration-matrix.md`
- `wails-architecture.md`
- `migration-plan.md`

退出条件：

- 所有旧页面和功能入口已列出。
- 配置、状态、提示、托盘、权限、更新和恢复语义已列出。
- 每个 UI 功能有目标页面、组件、后端接口和验收方式。
- Wails API 有集中适配边界。
- 普通权限 Host 与高权限 Core 的边界明确。

状态：本轮完成后进入 P1。

## 2. 阶段 P1：首页静态原型

允许范围：

- Wails v3 工程壳。
- React + TypeScript + Vite。
- Fluent UI React v9 与 Fluent Icons。
- 自定义标题栏。
- 1120×800 窗口、紧凑导航。
- 首页静态原型。
- 浅色/深色。
- 两张模拟网卡。
- 模拟 starting/running/stopping。
- 模拟速度、连接、权重、体检和底部核心状态。
- Wails v3 系统托盘原型。

禁止：

- 真实 Core。
- 真实网卡。
- 系统代理、TUN、WFP、路由、DNS。
- 其他页面实现。
- 删除或替换 WPF/Python。

实现顺序：

1. 建立独立 `desktop/`，不触碰现有 WPF。
2. 锁定 Wails v3 Alpha、React、Vite、Fluent UI 版本。
3. 建立 `platform` 接口和 Wails 适配器，即使原型只有 Window/Tray。
4. 建立 FluentProvider 和 HypoMux 主题。
5. 实现标题栏与紧凑导航。
6. 实现首页信息层级和两张模拟网卡。
7. 实现模拟状态机和克制动效。
8. 实现托盘显示、隐藏和退出。
9. 构建并运行。
10. 截图浅色和深色 1120×800。
11. 根据截图至少修正一轮。
12. 停止，等待产品确认。

验收：

- `frontend build` 成功。
- Go 编译成功。
- `wails3 dev` 实际运行。
- `wails3 package` 或 Windows package 实际执行并记录。
- 托盘显示和退出。
- 关闭按钮隐藏到托盘。
- 100%、125%、150% DPI。
- 1120×800。
- 深浅色。
- WebView2 缺失行为已设计；若当前机器无法卸载验证，记录为阻塞的环境测试而不是伪造通过。
- 浅/深色截图和一轮视觉修正记录。

退出门禁：

- 用户确认首页视觉、密度、导航和状态表现。
- 未经确认不进入真实 Core 接入。

## 3. 阶段 P2：只读 Host 与 Core 契约

目标：

- 不控制网络，只读取 Core hello/status/health/telemetry/log。
- 建立重连、超时、错误和 capability negotiation。
- 新增正式网卡枚举契约。

交付：

- `CoreClient`。
- engine session/sequence 隔离。
- 首页真实只读网卡与遥测。
- Core 不存在、版本不兼容、崩溃、超时的恢复 UI。

验收：

- 启动/关闭 UI 不泄漏 Core。
- malformed JSON、有界消息、超时测试。
- UI 重启可通过 status 重建状态。

## 4. 阶段 P3：设置与配置迁移

目标：

- 合并 `config.json` 和 QSettings 的重复配置。
- 提供 v2.2.0 一次性迁移和回滚备份。
- 实现设置页与个性化。

顺序：

1. 类型化配置 schema。
2. 迁移器与备份。
3. 语言、关闭行为、端口。
4. DNS/DoH。
5. 深浅色、强调色、Mica。
6. 背景图与表面不透明度。
7. 开机自启和配置目录。

验收：

- 旧配置逐字段迁移。
- 损坏配置回退。
- 写入原子性。
- 设置失败不覆盖旧值。
- 中英文完整。

## 5. 阶段 P4：普通代理控制

目标：

- 接入 Go ordinary proxy start/stop。
- 系统代理事务和恢复由 Go/平台服务拥有。
- 首页进入真实控制路径。

验收：

- SOCKS5 和 HTTP CONNECT。
- 轮询与权重。
- IPv4/IPv6。
- DNS/DoH 五种策略。
- 适配器故障/恢复。
- 停止、UI 崩溃、Core 崩溃后系统代理恢复。
- 停止后速度归零且迟到事件不回填。

## 6. 阶段 P5：分流规则

目标：

- 进程/域名/IP/CIDR 规则编辑。
- 运行中进程选择。
- 导入/导出。
- 规范化和权威校验移入 Go 服务。

验收：

- v2.2.0 规则和备份格式兼容。
- 重复/非法提示一致。
- 聚合、动态网卡、直连出口完整。
- TUN 运行中编辑显示重启生效。

## 7. 阶段 P6：网络体检与支持日志

目标：

- 网络体检页。
- 首页健康回写。
- 诊断日志查看、打开目录和导出。

验收：

- ICMP + 绑定 TCP。
- 丢包/延迟/抖动/配置检查。
- 诊断取消和退出安全。
- 日志最近 3 次、5 MiB、脱敏和限流语义保留。

## 8. 阶段 P7：TUN、WFP 与权限 Broker

目标：

- 普通权限 `asInvoker` UI + 正式版高权限 Core Windows Service。
- 安装时提升一次并注册服务；开发版服务未安装时按需 `runas`。
- TUN 两阶段启动。
- WFP 预检、修复、兼容状态。
- 外部联网验证、看门狗与受控重启。

验收：

- UI 进程令牌非管理员。
- TUN 操作触发明确权限请求。
- 用户取消后无网络变化。
- 第三方 TUN 和同网关风险。
- DoH/WFP 只重试一次。
- 两个 TUN 会话不重叠。
- 成功前必须通过真实联网证据。
- 停止/崩溃后无路由、Wintun、sing-box 和 WFP 残留。

## 9. 阶段 P8：域名隔离管理

目标：

- 保留用户可见“单网卡域名隔离”功能。
- UI 读取 Go Core domain quarantine，而不是复刻 Python 探测。
- 明确普通代理有域名可见性，TUN 不声称具备。

验收：

- 列表、删除、清空、到期和事件刷新。
- 配置迁移。
- 所有网卡失败时不误判。
- TUN 页面不展示虚假域名归因。

## 10. 阶段 P9：关于、更新与发布

目标：

- 关于、合规、SignPath 和赞助内容。
- 更新检查、Release Notes、下载、校验和安装。
- Wails v3 Updater 只作为适配器；必须满足现有安全语义。

验收：

- 只接受正式仓库和合法安装包名。
- 版本、大小、摘要/签名验证。
- 网络恢复完成后才安装。
- 安装、升级、回滚和临时文件清理。
- WebView2 Runtime 缺失提示。

## 11. 阶段 P10：生产切换

前置条件：

- 所有矩阵项验收通过。
- 中英文、键盘、无障碍和 DPI 通过。
- 安装/升级/卸载通过。
- 普通代理/TUN/崩溃/睡眠/网卡变化恢复通过。
- 至少一个候选版本完成真实 Windows 证据矩阵。

切换步骤：

1. 新前端成为可选启动路径。
2. 保留旧前端回滚。
3. 发布候选版本。
4. 收集至少一个发布周期证据。
5. 再决定移除 WPF/Python UI。

## 13. 失败与回滚

- P1 原型完全隔离，可删除 `desktop/` 而不影响现有发布。
- 新 Core 接口必须 additive；旧客户端仍可使用协议 v1。
- 新配置迁移先备份，失败保留原文件。
- 任何网络控制阶段失败都回到旧前端和已验证 Core。
- 不以“代码能编译”代替运行、截图、网络恢复或安装证据。
