# 算法与性能优化方案

日期：2026-09-11。范围：Go 引擎；第一阶段在本次实现，后续阶段独立验证和上线。

## 目标和阶段

| 阶段 | 工作 | 验收重点 |
| --- | --- | --- |
| 1 | DNS 缓存与域名隔离过期索引；按网卡绑定隔离的 DoH 连接复用 | 缓存命中和无过期项的调度不随记录数线性变慢；HTTP/1.1 复用及 HTTP/2 并发；TTL、隔离、取消与回退保持正确 |
| 2 | 容量感知的自适应网卡调度 | 混合长短连接、快慢网卡、链路速率变化下，比较总吞吐、完成时间、失败率与分配稳定性 |
| 3 | Steam 按并发负载分组的时间窗口统计，随后试验滑动窗口/折扣 UCB | 同网卡、同域名的可比样本；总吞吐收益；探测成本；退化撤销；不能将单连接峰值当作净收益 |
| 配套 | 普通拨号 Happy Eyeballs 式错峰竞速；按性能剖析结果优化 Steam 统计锁 | 建连 P50/P95/P99、失败率；锁等待及每 GiB CPU 开销 |

第二阶段先建设有效负载/拨号计数与容量估计，再调整权重。吞吐低可能来自应用需求不足，不能直接作为低链路容量的证据。对权重更新限速并保留探索，只影响新连接。第三阶段与第二阶段分别验证，避免两个反馈环同时变化而无法归因。

## 第一阶段设计

### DNS 过期索引

- 缓存结果仍由原来的五元键（网卡名、源 IPv4、接口索引、域名、记录类型）定位。
- 查询命中时只检查该条目的截止时间；到期即删除，不能返回过期答案。
- 使用可更新/删除的最小堆，每个键只保留一个截止时间。续期不会积累旧堆节点。
- 插入和状态快照清理到期项；容量满时仍淘汰最早到期项，不改变为 LRU。
- 命中平均 O(1)，插入/删除 O(log N)，清理 K 个到期项 O(K log N)。缓存容量和 TTL 上限、零 TTL 不缓存、同键在途请求合并保持原有行为。

### 域名隔离过期索引

- 每张网卡维护独立的域名截止时间索引，供调度、证据写入、状态快照清理到期项。
- 比较失败证据续期时更新原堆节点；成功时同时删除证据和堆节点；恢复的种子记录同样建索引。
- 保留证据门槛、隔离 TTL、关闭自动过期时的现有长期截止时间，以及所有网卡隔离时的回退语义。
- 无到期项时每张网卡只查看堆顶；大量记录同时到期仍有一次批量清理成本，不能宣称所有操作都为严格 O(1)。状态输出仍需遍历并排序实际记录。

### DoH 连接复用

- 使用标准库 HTTP Transport，支持 HTTP/2，并在端点仅支持 HTTP/1.1 时复用持久连接。
- 按网卡名、源 IP、接口索引和完整端点（IP、Host、Path）隔离连接池；拨号仍经过现有源地址绑定函数。
- 不使用环境代理、系统默认拨号或额外系统 DNS；保持 TLS 证书和 Host/SNI 校验，拒绝自动跟随重定向。
- 每个 Transport 最多 8 条连接、2 条空闲连接，空闲超时 30 秒；HTTP/1.1 可以并行处理冷查询，HTTP/2 复用连接上的流。每个解析器最多保留 64 个 Transport，超出时移除最久未使用的池并关闭其空闲连接。
- 请求取消由 HTTP Transport 处理，不在复用 socket 上设置每请求 deadline。共享 HTTP/2 连接上的一个请求取消不能中断其他请求。
- 标准库可能让连接建立继续服务其他等待请求，因此 TCP+TLS 建立另受 QueryTimeout 限制，并关联解析器根上下文；引擎停止时取消建立过程并关闭空闲连接。
- 保留 DoH 分批竞速、auto 策略给传统 DNS 预留预算、明确指定 DoH 时不降级明文的行为。响应体仍限制为 64 KiB，另限制响应头为 16 KiB。

## 验证与性能记录

第一阶段采用真实本地 TLS 服务验证复用、HTTP/2 并发、证书验证、响应校验和取消；不向公网发送测试 DNS 请求。过期索引用随机操作与简单映射作对照，并检查续期、删除、边界到期和恢复种子。

基线：Windows/amd64，Intel i7-13700H，Go 1.26.6；每组 200 ms、重复 3 次，以下为中位数。测试仅测 CPU 路径，数据未过期，无公网和真实下载负载。

| 基准 | 规模 | 优化前 ns/op | 优化后 ns/op |
| --- | --- | ---: | ---: |
| DNS 缓存命中 | 1 | 341.4 | 305.6 |
| DNS 缓存命中 | 1,024（默认容量） | 10,289 | 303.8 |
| DNS 缓存命中 | 16,384（压力规模） | 209,259 | 305.0 |
| 双网卡选择 | 每网卡 0 条证据 | 281.7 | 267.8 |
| 双网卡选择 | 每网卡 1,024 条证据 | 16,779 | 320.7 |
| 双网卡选择 | 每网卡 8,192 条证据（压力规模） | 144,003 | 385.3 |

1,024 条记录时，两条 CPU 路径分别约为基线的 34 倍、52 倍速度；缓存命中的 64 B / 3 次分配和双网卡选择的 768 B / 4 次分配未变化。索引额外占用 O(N) 内存，每条记录保留一个节点及其定位映射。压力规模的调度结果存在调度/GC 噪声；不将亚微秒差异解读为严格常数耗时保证。

本地 TLS 集成验证：HTTP/1.1、HTTP/2 分别连续 5 次查询只建立 1 条连接；HTTP/2 单连接并发 5 个请求、取消一个后其余成功；HTTP/1.1 可同时处理 8 个冷查询。不同网卡名、源 IP、接口索引和端点 IP/Path 分别建立池。覆盖证书/主机名拒绝、重定向拒绝、响应状态/类型/长度/DNS ID 检查、响应体超时、根取消中断 TLS 建立及关闭空闲 socket、池容量淘汰。

- `go test ./internal/... -count=1 -timeout=45s` 通过，包含 DNS、代理、运行时和引擎服务层的全部内部包。
- `go vet ./...`、命令入口测试编译（`go test ./cmd/hypomux-engine -run '^$'`）及 `git diff --check` 通过。

微基准的函数加速比不能换算为下载速度提升。实际收益需固定网卡、DNS 策略与任务，对照 DNS 延迟、总下载字节/时间、CPU、失败率和 Steam 磁盘活动。
