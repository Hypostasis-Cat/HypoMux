# 低延迟优先：本地调度方案

## 范围与使用

选择“低延迟优先”（协议值 `latency-first`），勾选至少两张具有独立可用网络的网卡，启动 TUN 模式。进入聚合池的应用自动使用此策略，不需要游戏端修改，也不依赖中继服务器。现有进程分流、直连规则、兼容性绕过和显式指定网卡规则仍优先：要让某款游戏参与调度，应让其进程进入聚合池。

本版本没有游戏名称识别数据库；策略覆盖聚合池内的流量，包括游戏。系统代理模式仅覆盖遵循代理配置的 TCP 应用，不能接管任意游戏 UDP。

## 测量与选择

- 使用现有 Windows 源地址绑定 IPv4 ICMP 诊断，每个目标每轮发一个探测包，单次最长 500 ms。最多 8 个并发探测任务。
- 持续探测两个参考地址 `223.5.5.5`、`1.1.1.1`。两者都只是线路质量参考，不能解释成实际游戏延迟。
- TCP 建连和 UDP 流量登记目标 IPv4；最多跟踪 8 个目标，30 秒不活跃后释放。UDP 发送会刷新目标活跃时间。每轮结束后等待一秒节拍；任务多或响应慢时周期会拉长，不保证每秒完成全部探测。
- 对同一个探测目标比较各网卡；每张候选网卡至少有 3 个样本，数据 8 秒后失效。优先目标 IP，其次参考地址；不能跨目标混合 RTT。第一次遇到某游戏时通常使用已有的参考估计，不能预知未测过的游戏线路。
- RTT 与抖动采用权重 0.25 的指数平滑，探测丢包率采用相同平滑。评分为 `RTT_ms + 2 × jitter_ms + 400 × probe_loss`，越低越好。此权重是初始工程参数，需要实际线路验证和调优。ICMP 丢包不等同于游戏数据包丢包。
- 连续 3 次探测失败的路径不作为有测量依据的优选。没有可信数据或全部不响应时，稳定选择首张健康候选，不反复轮询、不凭 ICMP 失败隔离整张网卡。
- 常规优选至少保持 10 秒，新线路需改善至少 8 ms 且达到原分数的 15%；明确的连续失败绕过这个保持时间。此机制主要作用于新连接选择。
- 不支持 IPv6 ICMP 测量，IPv6 流量按地址族过滤后稳定选择可用网卡，不套用 IPv4 测量。代理域名尚无目标 IP 时使用参考估计，不调用系统 DNS 来测速。

## 会话与故障恢复

TCP 已建立连接不迁移；新连接及原有建连重试使用当前健康候选和低延迟评分。调度不拆分、不重放已有 TCP 数据。

UDP 保持流内网卡绑定。轻微 RTT 或抖动变化不会主动破坏正在通信的会话。仅在以下条件同时满足时，于下一次出站数据包到来时重建上游 UDP 流：

1. 当前流至少 3 秒没有收到上游回复（新流也获得 3 秒观察期）。本地 UDP 写入成功不当作远端健康证据。
2. 当前网卡对某个此前响应过的目标连续至少 3 次探测失败；备用候选对同目标的探测数据新鲜、没有连续失败，且 3 秒内响应过。
3. 上述对比证据来自游戏目标 IP，或者同时来自两个参考地址。仅应用安静、仅某个公共节点失联、目标从未响应 ICMP，都不足以触发。

重建保留客户端 SOCKS UDP relay 和控制连接，排除旧网卡，为**尚未发送**的新数据包选择其他网卡；不复制或补发历史游戏包。显式本地网络读写错误会记录网卡故障，关闭旧上游，随后数据包重新选路。远端拒绝和普通读取超时不污染网卡健康。

不主动为已有健康 UDP 流追逐稍低的延迟。对于持续抖动但仍有正常回包的连接，新连接会择优，已有连接维持绑定，以避免出口变化导致掉线。

预期恢复量级是秒级：至少需要静默观察期、连续探测证据以及下一个应用包。探测超时、任务数量、游戏发包周期会延长恢复。对于目标/参考探测均被屏蔽的静默黑洞故障，不能保证检测；不设置无依据的“无回包即断网”规则。

切换仍可能改变公网 IP/端口；游戏服务器是否接受由游戏协议决定。本地保留 relay 并不保证游戏登录态或服务器会话连续，不能承诺无感切换。已有 TCP 需要应用自行重连。

## 协议、资源和兼容性

- `engine.hello.scheduling_strategies` 新增 `latency-first`；客户端保存和启动时检查旧引擎是否支持。
- `engine.start` 与 `engine.scheduling` 使用同一策略值，设置可持久化和运行中切换。
- `engine.telemetry.scheduling.latency` 提供每个网卡/目标的 RTT、抖动、探测丢包率、样本数、连续失败、更新时间、最后回复时间和 `target-icmp` / `reference-estimate` 来源。
- `scheduling.decisions` 提供目标探测、参考估计、学习回退和不支持目标的选择计数。`state=estimating` 表示此策略使用探测估计，不能当作游戏实测 RTT。
- 测量按网卡名称、源 IP 和接口索引组合隔离；网卡重新绑定不会继承旧地址测量。探测不修改全局网卡健康，不会因一个目标不可达导致其他流量被隔离。
- 探测仅在选中该策略时执行；停机等待所有有界探测完成。目标和旧绑定定期清理。

## 验证与实际验收

自动测试覆盖目标优先、参考回退、防抖、失效数据、全体屏蔽 ICMP、地址重绑定、排除候选、IPv6 回退、探测资源上限及取消、设置持久化和真实本地 SOCKS UDP relay 重建。

发布前仍需两条真实独立网络和游戏测试，分别记录：进入对局的线路、目标/参考测量来源、切换前后公网出口、首个恢复回包的时间、游戏是否重连。场景包括拔网线、网卡保持在线但上游断网、丢包抖动、恢复后反复波动、游戏/参考地址屏蔽 ICMP，以及双方网络同时失效。自动化本地回显测试不能替代这些结果。
