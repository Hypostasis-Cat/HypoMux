# 自适应最大速度调度设计提案

日期：2026-09-20。状态：设计提案，尚未实现或完成性能验证。

## 结论与现状

建议将“最大速度优先”重新设计为反馈驱动的连接级调度器，优化可观测的聚合下载吞吐，并以任务完成时间验证收益。不能承诺任意网络、任意应用上的全局最优。

代码依据：

- `desktop/frontend/src/components/home/schedulingStrategies.ts` 将 `maximum-speed` 映射为 `weighted: false`；说明文案明确是轮流分配。
- `engine/internal/proxy/scheduler.go` 的非加权分支是轮询；加权分支是平滑加权轮询。两者都没有速度反馈。
- `engine/internal/proxy/dial.go` 在连接建立前选网卡，并做地址族检查、绑定和失败重试；当前最多尝试两张可用网卡。
- `engine/internal/proxy/registry.go` 已有连接与网卡级双向字节计数，但存活连接数不等于正在下载的连接数。
- `engine/internal/proxy/server.go` 的 relay 已对 Steam CDN 采样并过滤部分客户端写入背压；聚合通道共享主 scheduler，指定通道另有 scheduler。
- `engine/internal/proxy/udp.go` 也调用 scheduler；TCP 算法不能未经区分直接改变 UDP 行为。
- `engine/internal/proxy/scheduling.go` 已支持运行时更新；连接继续保持原绑定。

## 优化目标与约束

主目标：在应用自然产生的连接、健康与路由约束下，提高稳定窗口内成功转发的下载字节率。辅助目标：降低可测下载任务的完成时间，避免连接失败率和短请求延迟明显恶化。

代理字节数包含应用协议开销；HTTPS 无法普遍识别有效文件字节、剩余文件大小或应用层重试。算法使用“转发吞吐代理指标”，外部压测使用校验后的有效内容和完整任务耗时。上传统计独立保存；第一版不宣称已经优化上传或实时 UDP。

已有 TCP/UDP 绑定不迁移，不拆单连接，不额外制造应用连接，不重放未知请求。流量全部是长期连接且不再新建时，调度器无法重新分配，收敛时间取决于连接更替。

## 算法：基于边际吞吐收益的自适应连接分配

核心问题是：下一条自然到达的连接放在哪张网卡，预计能增加最多的总吞吐？仅按当前速度动态加权会形成反馈偏差：分到更多连接的网卡速度更高，没有流量的网卡则永远无法证明自己。

### 1. 采样与上下文

在引擎中周期采样，不依赖前端轮询。初始建议 1 秒采样、5 秒决策窗口；这些是待压测的参数，不是已经验证的最佳值。

每张网卡记录双向字节增量、传输活跃连接数、待拨号预留数、连接建立耗时、失败率、客户端写入阻塞比例、样本年龄和置信度。连接活跃度由近期传输窗口平滑判断，避免把空闲 keep-alive 当作满载，也避免瞬时断流导致负载骤降。

以“网卡绑定代次 × 地址族 × 传输协议 × 目的上下文”保存观测。上下文优先使用已有可信域名；纯 IP 的 TUN 流量使用目的 IP 和端口，不假设一定能获得域名或进程。初版不依赖新增进程识别，不解密 HTTPS。域名样本不足时逐级回退到网卡级先验。

网卡级状态反映总负载，目的上下文修正特定下载源的差异。实际 CDN 端点已知时作为采样标签，不能把连接后才知道的端点当作拨号前已知输入。目的样本设 TTL 与数量上限，例如初始 10 分钟、4096 个上下文，淘汰非活跃项。

### 2. 学习吞吐—并发响应曲线

对网卡 i、上下文 c，维护 F(i,c,n)：该上下文有 n 个传输活跃连接、在当前其他负载下的预期总转发速率。按并发桶保存稳健平滑统计、波动范围和样本年龄，定期衰减旧样本。

仅用相邻负载、相近时间、相同目的条件的样本估计边际收益；混合负载变化大时降低置信度。不能把相隔很久的两次测量相减后声称是新增连接的因果效果。曲线用于短期局部预测，不能把历史峰值当成链路容量，也不能强制曲线永远单调增长而掩盖真实拥塞退化。

初始近似可用 F(n)=min(C,n*r)，其中 C 是近期有需求时观测到的平台速率估计，r 是同类连接的速率估计；样本不足时 C 未知，该近似只用于低置信度排序。逐步使用实际并发桶替代近似。流量不足不等于网卡容量下降。

负载 n 包含实际活跃连接、短暂的启动连接与待拨号预留。不同目的共享同一网卡负载预算，不能给每个域名重复计算一整条空闲链路。

### 3. 选择规则

健康、域名隔离、地址族和显式路由规则先限定候选；保留现有全部受限时的恢复路径语义。下载类连接的候选得分为：

```text
gain(i) = F(i,c,n_i + 1) - F(i,c,n_i)
score(i) = (1 - p_fail(i,c)) * gain(i) - loss(i,c)
```

gain 与 loss 均为字节/秒；loss 是基于观测估算的对现有传输或其他链路的吞吐损失，未知时不捏造数字，而是降低置信度。共享瓶颈尚未有证据时 loss 不直接套用固定惩罚。

对置信度足够且收益可区分的候选选择得分最高者；差异落在噪声范围内时选择预留与活跃负载较低者，再稳定轮转。所有边际收益接近零时仍接收连接，不因预测饱和而拒绝业务。

未知类型的新连接根据同目的历史和网卡先验判断，冷启动使用带预留的均衡探索。明确短请求上下文优先考虑连接建立耗时及失败率；不能在连接创建时假装知道未来是大下载或知道剩余字节数。第一版不将未经证实的 TCP 拨号时间称作 RTT。

### 4. 探索与反馈控制

初始为可用链路分配有限的自然连接以建立观测，避免启动时全部压到一张卡。稳定后给低置信度、样本陈旧的健康链路少量新连接，例如初始目标约 5% 的新连接、每张网卡最多一个未完成评估的探索预留。采用确定性预算方便测试；具体预算待实验调优。

探索比例是连接数比例，不是字节或耗时上限：一个长连接可能传输很久，不能承诺探索流量只有 5%。健康检查恢复预算与性能探索分别管理，不能绕过隔离规则。

后台控制器在可比较窗口中检查聚合吞吐是否改善，每次限制分配偏好的变化幅度；短暂尖峰不更新长期偏好。每个探索保存基线、其他负载、CDN 代次与观测窗口；条件变化则标记不可归因，不作成功/失败学习。探索停止只改变后续分配，不终止已经建立的连接。

在共享宽带、下载源限速或客户端背压下，如果新增分配长期没有聚合收益，降低继续倾斜的力度。吞吐相关性只是共享瓶颈线索，不足以判定两张网卡共用出口。

### 5. 并发与生命周期

选择与预留必须在同一临界区完成，防止并发拨号都看到相同空闲状态。建议引入 Acquire(context) -> (adapter, lease)；失败/取消调用 Release，Attach 成功原子转为活跃状态，Finish 释放且保持幂等。

预留必须覆盖 DNS 与拨号阶段；重试前释放原预留，再为下一张卡申请。不得在持有调度锁时做网络请求、扫描全部连接或计算模型。采样发布不可变快照，选择路径只遍历候选网卡，复杂度 O(网卡数)。

配置更新采用代次标记：网卡来源 IP/接口索引改变时重置该绑定模型，旧连接结束不得扣减新代次计数。策略切换、回滚、超时、引擎停止与重复 Finish 均需覆盖。预留到活跃的转换避免瞬时双计或漏计。

| desktop 服务与 schedulingStrategies.ts | 持久化真实策略，展示学习/稳定/样本不足及选择原因 |

建议增加 strategy 枚举 round-robin / weighted / adaptive-throughput。没有新字段时保持旧 weighted 的原有语义；新桌面端仅在核心声明能力时发送新策略。迁移旧“最大速度优先”配置时应明确升级后的行为，并保留轮询作为回退基线。实现需贯穿引擎启动、持久化、协议能力协商和事务回滚，不能仅改前端映射。

指定网卡连接继续遵守指定规则；它们的流量可以计入该网卡负载，但不能当作聚合调度探索样本。直连负载在网卡归属未知时不强行归因；系统外部流量对容量的影响通过反馈反映，可后续加入只读 OS 计数辅助判断。

Steam CDN 选择与网卡选择分层：先选网卡，再在该网卡内由现有 CDN 机制选择端点。两个控制器的实验需共享代次/标签；同一上下文避免同时做网卡与 CDN 探索，否则样本只记吞吐、不作调度收益归因。已有 CDN 采样的背压过滤经验可复用，数据不应无条件直接合并。

## 验收与实施顺序

1. 先接入性能采样与影子决策，实际仍轮询；验证样本、代次、锁竞争与决策理由。影子运行只能验证可运行性，无法证明未选择路径的实际收益。
2. 实现自适应 TCP 策略和确定性测试：冷启动、快慢链路、并发拨号预留、空闲连接、失败取消、旧代次结束、配置回滚、饥饿恢复、数据过期、指定通道与 UDP 边界。
3. 用可控服务器/限速链路进行真实对照，再做 Windows 多网卡实测。模拟器必须采用独立的链路/下载模型，不能拿调度器自己的预测作为结果。
4. 通过结果决定是否把首页“最大速度优先”迁移到新策略。

比较对象：现有轮询、手动合理权重、只用最佳单卡。测试顺序随机化并重复，统一文件、下载源、总并发、连接更替与 CDN 配置，记录置信区间。

必测场景：100/100、100/20、100/5 Mbps 独立链路；少量和大量并发；单连接及永久长连接；容量骤降后恢复；两卡共享限速出口；单连接服务器限速；混合下载源；高延迟链路；客户端磁盘/读取背压；UDP 与短 TCP 混合；网络断开、IPv6 差异及运行时删卡。

测量：校验后有效内容吞吐、总任务耗时及尾部耗时、连接建立 p95、失败率、恢复到稳定分配的时间、新连接分布、探索实际字节占比、CPU/内存与调度耗时。只有存在自然新连接时才报告调度收敛指标。

暂定发布门槛（待形成基线后确认）：关键非对称多连接场景收益的置信区间下界大于零；对称/单卡对照无超过 5% 的稳定吞吐回退；连接正确性与现有路由、健康、回滚测试全部通过；p95 建连开销不显著恶化。不能仅凭某次峰值或模拟结果宣称最大速度已实现。

## 理论参考与适用边界

- [RFC 6356](https://www.rfc-editor.org/rfc/rfc6356.html)：讨论多路径资源共享与共享瓶颈，明确可靠识别共享瓶颈很困难。这里借鉴问题定义，不移植 TCP 拥塞控制公式。
- [STMS, USENIX ATC 2018](https://www.usenix.org/conference/atc18/presentation/shi)：针对异构路径的 MPTCP 包调度与接收侧问题。HypoMux 是独立连接调度，不具备其 MPTCP 发送窗口与确认信息，不能直接照搬或声称同等收益。

本提案是针对现有代码约束的工程设计，不是已有实测结论，也不主张算法学术创新。
